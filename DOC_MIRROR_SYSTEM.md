## 2. THE ALGORITHM (no random documents — this is the law)

```
For any codebase C:

  1. ENUMERATE every module m ∈ C  (a "module" = one source file, or one cohesive unit).

  2. READER/WRITER agent per m → writes doc(m): a 1:1 explanation of m.
        - One module ⟷ exactly one doc. Deterministic mapping.
        - doc(m) explains m completely: every class, function, signature, what it does, why.
        - Cite m by path. The doc IS the module, explained.

  3. SYNTHESIZER reads all doc(m) → writes the CONNECTION layer:
        - the 6 top-level files (the index/navigation: project-overview, architecture,
          code-standards, ai-workflow-rules, ui-context, progress-tracker)
        - cross-module synthesis docs (named by the modules they connect, not by session/topic).

  4. ON a code change to module m:
        - FORK doc(m) → doc(m) is re-derived from the changed module (versioned).
        - re-run the SYNTHESIZER over the affected docs.
        - NEVER edit doc(m) in place silently. NEVER write a standalone "fix writeup."

  5. THE JOURNAL = the dated THINKLOG. Records what you THOUGHT/DECIDED (intent, decisions + why,
     open forks, "updated vision then impl") — the cognition behind changes. It is ONE global index
     (`$DOCMIRROR_JOURNAL_DIR/YYYY-MM.md`, lines "{now} UPDATED {repo}: {msg}") that PROJECTS to a
     per-repo file (`<C>/context/journal/YYYY-MM.md`, lines "{now} {msg}"). Appended via `journal "{msg}"`.
     This is DISTINCT from `git log` (the changelog of what CHANGED) — git log is not the journal.

INVARIANT (the law): every file in the system is EXACTLY ONE of:
  (a) doc(m) = IMPL — what module m ACTUALLY IS in code (docs/mirror/<relpath>.md), made FIRST,
  (b) vision(m) = VISION — ideas/decisions about m NOT (yet) in code (docs/vision/<relpath>.md), paired 1:1.
      Each entry is a tagged HYPEREDGE (tags:[modules,repos,concepts]); a multi-target vision is ONE canon
      file at its first-tagged home + RELATIVE SYMLINKS everywhere else it's about (git mode-120000;
      closure/find follow them; edit-canon-updates-all). Never duplicate as copies — one canon, N symlinks.
  (c) a synthesis of named modules,
  (d) one of the 6 top-level index files,
  (e) a repo-local rule/skill,
  (f) the dated thinklog (global index + per-repo projection).
NOTHING ELSE. **IMPL FIRST, THEN VISION:** doc(m) is code-only; ANY unimplemented idea goes in vision(m),
never in doc(m); an idea moves vision(m)→doc(m) only when built. The journal PROJECTS out: decision/idea
→ vision(m), built → doc(m), BUG → GitHub issue (rules/skills stay manual per 2026-05-30; everything else
auto-projects). A DATED thinklog file is legal (kind f); the disease is topic/fix/session-NAMED docs AND
unimplemented ideas living in impl docs. If a doc is not one of the six, it does not belong — delete or fold it.
```

## 4. RELATIONSHIP TO THE SIX-FILE METHODOLOGY

- **Six-file methodology** (`<repo-root>/six_file_methodology/` README + templates;
  global rule `six-file-context-methodology.md`): the **6 top-level files in `context/`** =
  project-overview, architecture, code-standards, ai-workflow-rules, ui-context, progress-tracker.
  These are the **navigation/index layer** (step 3 above). They POINT DOWN to the knowledge layer.

  feeds up into the 6 files.
- There is **no six-file "skill"** today — only the rule + Adrian's templates dir. The doc-mirror IS the
  knowledge layer the six-file methodology assumes exists beneath its 6 files.
- **`context/` is currently polluted** (asset-inventory, drew-bangerlab-timeline ×2, timeline-thread-report
  sit next to the 6 files). Booting the system includes cleaning `context/` down to exactly the 6 files +
  pointers, moving the rest into the journal or deleting.
